# 速率与配额

AIKanHub 对每个用户账户施加速率上限，防止单用户独占平台资源。速率按**用户账户**计，不按 API Key —— 同一账户下所有 Key 共享同一份配额。

## 各套餐限速

| 套餐 | 每分钟提交（Total） | 每分钟成功完成（Success） |
| --- | --- | --- |
| Trial | 40 | 20 |
| Beta | 60 | 40 |
| Paid | 240 | 200 |

> **提交**：调用 `POST /v1/video/generations` 的次数。
> **成功完成**：上一项里返回成功响应（可入排队）的次数。两者都触顶任意一个会立即被限制。

视频生成单次耗时较长（通常 30–60 秒），所以"每分钟成功提交"近似等于"账户的最大并发任务数"。

## 触发限速时怎么办

超出阈值时接口返回：

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json

{ "error": { "code": "rate_limit_exceeded",
             "message": "Too many requests from this user, please try again later." } }
```

处理建议：

1. **指数退避**：第一次等 5 秒，第二次 10 秒，第三次 20 秒，最多到 60 秒。
2. **不要并发硬刷**：与其同时提交 50 个任务，不如保持稳定 10 并发的"水管"模型。
3. **查正在进行的任务**：通过 `GET /v1/tasks/{id}` 轮询不计入提交速率。

## 平台级公平使用

为了在所有用户间公平分配后端算力，平台对**全局并发任务数**也有保护性上限。这个上限：

- 大于所有套餐的成功速率之和（所以正常使用不会被它卡住）。
- 在极端突发场景（多用户同时刷批量）下生效，表现为偶发的 5xx + 自动退款。
- 你不需要为它显式编程，正常的退避重试就足够。

## 钱包额度（Quota）

钱包额度是另一道保护，**不是速率上的限制，而是消费上的限制**。

- 提交任务时 AIKanHub 会预估消费、预扣额度。
- 钱包余额不足以覆盖预估时直接返回 402，**不会发到后端**，也不会进入排队。
- 任务完成时按实际规格多退少补；失败全退。

详见 [Billing & Credits](./billing.md)。

## 自托管 API Key 的额度上限

每个 `sk-xxx` Token 在创建时可以指定一个额度上限（也可设为无限制）。这是**软限制**，作用是让你在前端拆分预算：

- 一个跑批 Key 给生产用，限额 5000 积分。
- 一个临时 Key 给同事用，限额 100 积分。
- 两个 Key 都从同一个钱包扣，但单 Key 触顶后会先于钱包枯竭返回错误。

Token 额度只能小于等于钱包；管理员不会通过 Token 额度反向拉高你的钱包。

## 常见误解

**"为什么我的 Trial 速率只有 20 / 分钟？我并发跑了 5 个 Worker 都没事啊。"**

20 是"每分钟成功完成的提交"。5 个 Worker 每个跑一个 30 秒任务，分钟级吞吐 ≈ 10，远低于 20，所以不会触发。**只有当每分钟有超过 20 次新提交都成功入队，才会到上限。**

**"能不能给单个账户买更高速率？"**

升级到 Paid 即可（详见 [Pricing](./pricing.md)）。如果 Paid 的 200/分钟仍不够，请联系销售商谈定制方案。

**"429 会扣我钱包吗？"**

不会。429 是请求被拒绝，没有进入排队，不预扣额度。

**"任务超时算谁的？"**

如果后端超时，任务被标为 `failed`，已预扣的额度全额退还，不影响速率统计。
